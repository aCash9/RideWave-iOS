RideWaveModel.swift · why the model is small

RidePage is only navigation state: tutorial, connect, or ride. It deliberately does not contain Spotify calls. This prevents a temporary disconnect from being confused with a navigation decision.

page = hasPlaybackSession ? .ride
      : (defaults.bool(forKey: "onboarding_seen") ? .connect : .tutorial)

func completeTutorial() {
    defaults.set(true, forKey: "onboarding_seen")
    page = .connect
}

Why necessary: onboarding should be remembered, but the current screen should still be derived from real playback-session availability. Tests can inject UserDefaults and a fake session flag without launching SwiftUI.

ContentView.swift · ownership and lifecycle

@StateObject keeps the controllers alive across SwiftUI redraws. There are two instances: ordinary playback and playlist Web API. scenePhase is forwarded to both.

  • spotify.connected → .ride: ride mode opens only after App Remote works.
  • !spotify.authorized while .ride: invalid/revoked authorization returns to connect.
  • onOpenURL: routes Spotify callbacks to both controllers, which then apply their own guards.
  • isIdleTimerDisabled: the display stays awake only during active ride mode.

Why necessary: SwiftUI views can be recreated frequently; the app-level object owns side effects and cleanup instead of placing them in transient view bodies.

2 · Spotify authorization and playback

SpotifyController.swift · the state machine

Three booleans describe different facts:

authorized
A valid Spotify session/token exists.
connected
App Remote is connected right now.
busy
Authorization, refresh, or connection is running.

wantsPlayback records intent, active records foreground state, and UUIDs identify the latest async attempt. Those are not redundant: they prevent an old task or callback from changing newer UI state.

Why necessary: OAuth can succeed while App Remote fails, and the app can go inactive while a connection task is still running. Separate state lets each failure be handled safely.

authorize → handleURL → accept · callback path
  1. authorize(playback:) checks client ID and, for playback, checks that Spotify is installed.
  2. It creates a new SPTSessionManager, marks authorizing, and starts a 120-second deadline.
  3. iOS returns to ridewave://callback.
  4. handleURL accepts only the expected scheme, host, empty/root path, no credentials, and a currently pending authorization.
  5. Spotify calls didInitiate; accept saves the session in Keychain and starts App Remote reconnect if playback was requested.

Why necessary: a URL callback is external input. The exact callback check prevents unrelated URLs or late callbacks from being treated as successful login.

accessToken · renewal and shared waiters

If the token has more than 60 seconds left, it is reused. Otherwise callers append continuations to refreshWaiters; only the first caller invokes renewSession(). When Spotify responds, finishRefresh resumes every waiter with the same result.

if !forceRefresh && session.expirationDate.timeIntervalSinceNow > 60 {
    return session.accessToken
}
// first waiter starts renewal; later callers join the same renewal
refreshWaiters.append(continuation)

Why necessary: playlist loading can make many requests. Without shared renewal, concurrent requests could race and invalidate each other.

setActive / reconnect / stopPlayback · lifecycle cleanup

When inactive, the controller cancels connection work, removes delegates, disconnects App Remote, clears player state, and marks connected = false. When active again, it reconnects only if wantsPlayback is still true. Closing ride mode sets that flag false.

Why necessary: Spotify connections are device resources. Explicit cleanup avoids stale delegates, duplicate connections, and reconnecting after the user intentionally closed ride mode.

perform and player state

Every tap/swipe checks for a live remote player API. Toggle additionally requires hasPlayerState, because the app must not guess paused/playing. Spotify player updates replace the title, artist, and paused state shown on screen.

3 · Web API playlists

SpotifyWebAPI.playlists · request loop

The method starts at /v1/me/playlists?limit=50. Before every request it checks cancellation, validates the URL, rejects visited URLs, and caps pages at 1,000. It accepts 200, maps 401/403/429/other statuses to user-facing errors, decodes nullable items, deduplicates by playlist ID, and follows a normalized next link.

Why necessary: pagination URLs are response data, not trusted constants. Validation prevents sending a bearer token to an attacker-controlled host and prevents cycles or unbounded work.

SpotifyRedirectPolicy and 401 behavior

The URL session refuses redirects entirely, so an Authorization header cannot silently travel to a new destination. A 401 causes exactly one forced token refresh and retry; a second 401 becomes an authorization error.

4 · Ride contacts

ContactNumberPicker → RideContact

The picker shows only phone properties and uses property selection, which means multi-number contacts open a number list. The coordinator converts the selected property into a RideContact. The contact model stores an ID, display name, normalized number, and optional resized image—not the complete address-book record.

Why necessary: selecting one property minimizes privacy access and avoids guessing which number to call.

ContactPhone and storage validation

Normalization permits digits and one leading plus while ignoring formatting. Extensions, star/hash codes, embedded URLs, and other special characters are rejected. Storage enforces at most four contacts, unique IDs/numbers, normalized numbers, and a 1 MB photo limit. Writes are atomic, protected until first unlock, and excluded from backup.

RideContactsView · timer and accessibility

The overlay auto-dismisses after five seconds, but the timer pauses while the picker, alert, edit mode, call, backgrounding, VoiceOver, Switch Control, or touch interaction is active. The same view keeps playback gestures behind the overlay and provides explicit accessibility labels for call/remove actions.

5 · How the tests relate to the code

ScreenFlowChecks

Injects isolated UserDefaults and verifies tutorial completion, persistence, and restored-vs-absent playback session behavior.

SpotifyWebAPIChecks

Uses URLProtocol mocks to verify pagination, deduplication, 401 renewal, HTTP errors, hostile links, malformed JSON, timeouts, and callback routing.

RideContactsChecks

Uses temporary storage to verify persistence, removal, capacity, duplicate normalization, safe phone URLs, unsupported numbers, and failed writes.

Still device-only: real Spotify App Remote, Keychain entitlements, iOS contact picker presentation, call confirmation, and physical Spotify playback require a signed iPhone.
